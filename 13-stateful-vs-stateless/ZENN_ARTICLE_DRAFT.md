# Cookie SessionとJWT Bearerの使い分け方：ステートフル/ステートレスを要件から選ぶ

## はじめに
Cookie SessionとJWT Bearer、結局どっちを使えばいいのか迷うことがあると思います。  
「JWTの方がモダンそうだから」という理由で選びたくなる場面もありますし、セキュリティ的にどちらが安全なのか判断しづらいこともあります。    
この記事では、ステートフル/ステートレスの違いを整理しながら、失効要件・システム構成・セキュリティ運用の3軸で判断できる状態を目指します。

## まず結論
Cookie Session は認証状態をサーバー側で保持するため、中央集権的に制御しやすい方式です。そのため、パスワード変更時の全セッション失効や、社内システムでの退職者権限剥奪のように、旧権限のセッションを即時に無効化したい要件に向いています。  
一方 JWT Bearer はトークン自己完結型で、分散構成やマイクロサービスで扱いやすい方式です。  
Web とモバイルで同じトークンを使ったり、BFF や複数 API をまたぐ構成でも、各サービスが同じ JWT を検証して認証を成立させられるのが強みです。

## 判断軸
どちらを選ぶかで迷ったときは、まずこの3つの軸で要件を整理すると判断しやすくなります。

### 失効要件
- どれだけ即時に無効化したいか
- パスワード変更・権限剥奪・不正検知時の強制ログアウトがあるのか

### システム構成
- 単一サーバー中心か、分散/マイクロサービスか
- サービス間で認証情報を受け渡す必要があるか

### セキュリティ運用（XSS/CSRFにどう向き合うか）
- どの脅威をどの運用で抑えるか
- Cookie運用なら `HttpOnly` + `SameSite` + CSRF対策が鍵
- JWT運用なら保存場所（`localStorage` 回避含む）と期限・再発行設計が鍵

## Cookie Sessionを選ぶケース
Cookie Session は、ブラウザに保存されたCookie（セッションID）を使って、サーバー側で認証状態を管理する方式です。クライアントには識別子（session id）のみを持たせ、実際のユーザー情報や認証状態はサーバー側に保持します。  
### 一言で言うと
Cookie Sessionは「あとから制御できる認証方式」です。

### 向いている要件

#### 即時失効が求められるケース
- パスワード変更時に全セッションを無効化したい
- 権限変更・退職時に即ログアウトさせたい
- 不正検知時に強制的にアクセスを止めたい

Sessionはサーバー側で管理されるため、削除すれば即無効化できます。
トークンのように「クライアントに残り続ける状態」がないため、後から止められる設計を取りやすい点が特徴です。

#### 認証状態を厳密に制御したいケース
- 管理画面・社内システム
- 金融系・個人情報を扱うサービス

例えば招待制アプリのように、認証状態を厳密に制御したいケースがあります。
認証情報の実体をサーバー側にのみ保持することで、クライアントからの改ざんリスクを抑えつつ中央集権的に制御できます。

#### セッション単位の制御が必要なケース
- 同時ログイン制限（例: 1ユーザー1セッション）
- 端末ごとのログアウト管理
- ログイン履歴の管理

業務用アプリでは、親会社・子会社・パートナー企業など立場ごとに権限制御が必要になることがあります。セッションを「接続単位」として管理できるため、ユーザー単位よりも細かい制御（端末・ログイン単位）が可能になります。

#### 状態をサーバーで持ちたいケース
- カート情報
- 入力途中のフォーム状態
- ユーザーごとの一時データ

下書き保存や一時中断のように、操作途中の一時データを扱いたいケースがあります。
認証と同じスコープで状態を保持できるため、「ログイン中のユーザー状態」を一貫して扱えるのがステートフルの強みです。

### 採用時の注意点
Cookie Session は安全に使えば強力ですが、設定を誤ると脆弱性に直結します。
ここでは最低限押さえるべきポイントを、役割ごとに整理します。

#### Cookie属性を必ず設定する

Cookieはそのまま使うのではなく、ブラウザ側での挙動を制御する属性を必ず付与します。

- **HttpOnly**
  - JavaScriptからCookieを参照できなくする設定
  - 目的：**XSS（スクリプトによるCookie盗難）対策**
  - 例：悪意あるスクリプトから `document.cookie` でセッションIDを抜かれるのを防ぐ

- **Secure**
  - HTTPS通信のときだけCookieを送信する設定
  - 目的：**通信経路での盗聴防止**
  - 本番環境では必須（HTTPだと盗まれる可能性あり）

- **SameSite**
  - 別サイトからのリクエスト時にCookieを送るかどうかを制御
  - 目的：**CSRF（なりすましリクエスト）対策**
  - 主な値：
    - `Strict`：完全に同一サイトのみ送信（最も安全）
    - `Lax`：通常のリンク遷移などは許可（実務でよく使う）
    - `None`：外部送信も許可（その場合はSecure必須）


#### CSRF対策をセットで設計する

Cookieは自動で送信されるため、**ユーザーの意図しないリクエストにも付与されてしまう**という性質があります。

- SameSiteだけに依存しない
- 必要に応じてCSRFトークンを導入する

**CSRFトークンとは**

- サーバーが発行する「正規リクエストである証明」
- フォームやヘッダーに埋め込み、サーバー側で検証する

ポイント：Cookieは便利だが「勝手に送られる」というリスクを持つ。

#### 有効期限と失効戦略

セッションは無限に有効にしてはいけません。
どのタイミングで無効化するかを明確に設計します。

- セッションTTL（有効期限）を定義する
- 無操作タイムアウト（一定時間操作なしで失効）
- 明示ログアウト時に確実に削除する

「いつまで有効か」を決めないとセキュリティは成立しません。

#### スケール時の共有ストア設計

複数サーバー構成になると、セッションの保存場所が問題になります。

- Redis などでセッションを共有する
- どのサーバーにアクセスしても同じセッションを参照できるようにする

さらに重要なのが、障害時の整合性です。

- セッションが消えない（ゾンビ化）
- 逆に早く消えすぎる（強制ログアウト多発）

Sessionは「どこに置くか」がスケーラビリティのボトルネックになります。

## JWT Bearerを選ぶケース
JWT Bearer は「認証情報をトークンとしてクライアントに持たせる」方式です。  
そのため、サーバーが状態を持たずに認証できる（ステートレス）構成に強みがあります。  
### 一言で言うと
JWT Bearerは「どこでも使える認証方式」です。

### 向いている要件

#### 分散 / マイクロサービス構成
- 複数のAPI・サービスが存在する
- サービス間で認証情報を共有したい

JWTを各サービスが検証するだけで認証が成立するため、セッション共有（Redisなど）に依存しない構成を取りやすくなります。

#### Webとモバイルなど複数クライアント対応
- Web / iOS / Android など複数フロント
- 同じ認証基盤を使い回したい

Cookieに依存しないので、クライアント種別をまたいで扱いやすいのが特徴です。

#### スケーラビリティを優先したい
- 高トラフィック
- オートスケール前提

サーバーにセッションを持たないため、状態同期コストを抑えながらスケールさせやすくなります。

#### サービス間連携（BFF / API Gateway）
- BFFパターン
- API Gateway経由で複数サービスを叩く

トークンを中継しやすく、各サービスで認証ロジックを共通化しやすい構成です。

#### 外部API連携 / OAuthベース
- 外部サービスと連携する
- 認可サーバーを利用する

JWTは標準的なフォーマットなので、OAuth2 / OpenID Connect と組み合わせやすいです。

### 採用時の注意点

#### トークンの保存場所
JWTはクライアントに保存する必要があるため、保存場所の選択が重要です。

- `localStorage`
  - 実装は簡単
  - XSSで盗まれるリスクがある
- `sessionStorage`
  - タブ単位で管理できる
  - 同様にXSSに弱い
- `HttpOnly Cookie`
  - JavaScriptから参照不可
  - XSS耐性を上げやすい
  - CSRF対策が必要

どの脅威を優先して防ぐか（XSS / CSRF）を先に決めて選ぶ必要があります。

#### 失効戦略（重要）
JWTは基本的に、発行したトークンが有効期限まで有効です。

ここがJWTの弱点になりやすく、「一度発行すると止めにくい」という特性があります。

- サーバー側で即時無効化しづらい
- 不正トークンを止めにくい

対策として、短い有効期限、リフレッシュトークン再発行、必要に応じたブラックリスト管理を組み合わせます。「どうやって止めるか」を設計しないと運用で破綻しやすいです。

#### 有効期限とリフレッシュ設計
- アクセストークン：短命
- リフレッシュトークン：長命

この2層構成で、UXとセキュリティのバランスを調整します。

### 運用メリット（なぜ選ぶのか）
- サーバーが状態を持たないためスケールしやすい
- サービス間で認証情報を共有しやすい
- Web / モバイル / API をまたいで使いやすい

### ここまでの補足
ここまで整理すると、JWT Bearerは「どこでも使える認証方式」で、分散構成やスケーラビリティを優先するシステムで強みを発揮しやすい方式だと分かります。

## よくある誤解
ここは、誤解されやすいポイントを整理して再確認します。

### 「JWTの方が常に安全」は誤解
JWTには「署名付きで改ざんされにくい」という特徴がありますが、それだけで安全性が保証されるわけではありません。

- 署名が守るのは**改ざん耐性**であり、**盗難耐性**そのものではない
- トークンが漏えいすれば、そのまま認証に使われる（Bearerの性質）
- 基本構成では、サーバー側で即時失効しづらい

JWTは便利な部品ですが、失効戦略や保存戦略を設計しないと、むしろ運用リスクが上がるケースがあります。

### 「Cookieは危険、JWTは安全」ではない
本質は「技術名」ではなく「保存場所と送信方法」です。

- Cookie運用
  - 自動送信されるためCSRFリスクはある
  - `HttpOnly` / `SameSite` / `Secure` で対策しやすい
- JWT運用（`localStorage` など）
  - 手動送信なのでCSRFは起きにくい
  - XSSでトークンが盗まれるリスクは高くなる

CookieかJWTかだけで優劣を決めるのではなく、脅威モデルに合わせて運用設計を選ぶことが重要です。

### BearerはJWTそのものではなく「運び方」
BearerとJWTは同じものとして扱われがちですが、役割が異なります。

- Bearer: `Authorization` ヘッダーでトークンを送る方式
- JWT: トークンの中身フォーマット

そのため、`Bearer + JWT` は一般的な構成ですが、`Bearer + ランダムトークン` も成立します。  
つまり、Bearerは「どう送るか」、JWTは「何を送るか」の違いです。

## 比較表

| 判断軸 | Cookie Session向き | JWT Bearer向き |
|---|---|---|
| 失効要件 | 即時ログアウト・強制失効を重視 | 短TTL + 再発行など失効戦略を前提に運用する |
| 状態管理 | サーバー側で状態を保持して集中管理したい | サーバー無状態でトークン自己完結にしたい |
| システム構成 | 単一/小規模構成中心 | 分散/マイクロサービス中心 |
| サービス間連携 | セッション共有ストアを前提に連携する | トークン中継で連携し、各サービスで検証する |
| 認証情報の運搬 | Cookie自動送信で管理したい | `Authorization: Bearer` を明示的に付与したい |
| セキュリティ運用 | `HttpOnly` / `Secure` / `SameSite` + CSRF対策を設計できる | 保存場所（XSS）と再発行・失効戦略を厳密に設計できる |
| スケール時の考慮 | Redis等の共有ストア設計が必要 | 状態同期コストを抑えてスケールしやすい |
| 通信コスト | 認証情報は軽量（sid中心） | JWTサイズ分の送信コストが増えやすい |

## 結局どう選ぶべきか
- 「あとから止めたい」なら Cookie Session
- 「スケール・分散したい」なら JWT Bearer
- 「ブラウザ中心」なら Cookie Session
- 「API / モバイル中心」なら JWT Bearer

自分のシステムにどちらが合っているかを考えると、方針を決めやすくなります。

## まとめ
- Cookie Sessionはストア方式で管理するため、制御しやすく、即時失効にも対応しやすい
- HttpOnly / SameSite / Secure などを適切に設定すれば、CSRFやXSSのリスクを抑えやすい
- JWT Bearerは、認証情報を共有したい分散構成やマイクロサービスで効果を発揮しやすい
- トークンをクライアントに持たせることで、ステートレスな認証を実現できる
- Web / モバイル / API など、クライアント種別をまたいで認証基盤を揃えやすい
- 最終的には「失効要件」「システム構成」「セキュリティ運用」の3軸で選ぶのが実務では判断しやすい
