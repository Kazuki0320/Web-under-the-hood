## 1. Keep-Aliveの基本

### 1-1. Keep-Aliveは何をしている？
疑問点:
- 「Keep-Aliveって、結局何が嬉しいの？」

こういう意味らしい:
- 1回作ったTCP接続を使い回して、複数のHTTPリクエストを処理する仕組み。
- 毎回 connect/close を繰り返さない分、通信の往復コストが減る。
- HTTPSならTLSハンドシェイクの回数も抑えられるため、体感速度に効きやすい。

### 1-2. HTTP Keep-Alive と TCP keepalive は同じ？
疑問点:
- 「名前が似ているけど同じ機能？」

こういう意味らしい:
- 別物。
- HTTP Keep-Aliveは「アプリ層で接続を再利用する」話。
- TCP keepaliveは「低レイヤーで死活確認する」話。
- 目的と効く場所が違うので混同しない方がよい。

## 2. HTTPバージョンと接続挙動

### 2-1. HTTP/1.1だと何がデフォルト？
疑問点:
- 「HTTP/1.1だと毎回 `Connection: keep-alive` を付ける必要がある？」

こういう意味らしい:
- HTTP/1.1では接続再利用が基本挙動。
- 明示的に `Connection: close` を指定したときは切断寄りになる。

### 2-2. HTTP/1.0はどうなる？
疑問点:
- 「HTTP/1.0だと同じように再利用される？」

こういう意味らしい:
- HTTP/1.0は切断ベースの挙動になりやすい。
- `Connection: Keep-Alive` を明示すると再利用されるケースがある。
- そのため、1.0と1.1で挙動比較すると差が見えやすい。

## 3. 切断はどちらが決めるのか

### 3-1. Keep-Aliveのタイムアウトはサーバー側だけ？
疑問点:
- 「接続の寿命ってサーバー設定だけで決まる？」

こういう意味らしい:
- サーバー側で keep-alive タイムアウトを持つのは一般的。
- ただしクライアント側にも「どれくらい接続を保持するか」の方針は持てる。
- 先に待機時間の上限へ達した側が、FINを送って切断を開始する。

### 3-2. クライアント側から切断を指示できる？
疑問点:
- 「クライアントから `close` を出すことはできる？」

こういう意味らしい:
- できる。HTTPヘッダーで `Connection: close` を送ると、次応答後の切断意図を伝えられる。
- 検証では次のように送れる。

確認コマンド:
```bash
curl -v -H 'Connection: close' http://localhost:8080/
```

観測ポイント:
- サーバーレスポンス側も `Connection: close` になるか
- 続けて同URLへアクセスした時に、再利用ではなく新規接続になるか

## 4. curl観測の見方

### 3-1. 再利用できたかはどこを見る？
疑問点:
- 「`curl -v` のどこを見れば接続再利用が分かる？」

こういう意味らしい:
- 再利用のサイン:
  - `Re-using existing connection!`
  - `Connection #0 ... left intact`
- 切断のサイン:
  - `Closing connection 0`
  - 次回が `Connection #1` など別番号で開始

### 3-2. 検証順はどう組むと分かりやすい？
疑問点:
- 「どんな順番で試すと理解しやすい？」

こういう意味らしい:
- 次の順番が比較しやすい:
  1. HTTP/1.1 で連続リクエスト
  2. HTTP/1.0 で連続リクエスト
  3. HTTP/1.0 + `Connection: Keep-Alive`
  4. `Connection: close` 指定
- クライアント指定で接続挙動がどう変わるかを切り分けやすい。

## 5. サーバー先行切断で起こり得ること

### 5-1. サーバー側タイムアウトが短いと何が起きる？
疑問点:
- 「サーバーが先に切る設定でも問題ない？」

こういう意味らしい:
- タイミング次第で「サーバーが切断しようとした瞬間」にクライアントが次リクエストを送る競合が起きる。
- この行き違いがエラー（プロキシ配下では 502 など）につながることがある。
- 中継系（CDN/LB）が前段にいる構成ほど、このズレが表面化しやすい。

### 5-2. じゃあどちらを短くするのが無難？
疑問点:
- 「運用上の基本方針は？」

こういう意味らしい:
- 実運用では、前段クライアント（LB/CDN）よりアプリ側のタイムアウトを少し長めに取る設計がよく使われる。
- 理由は、接続終了の主導権を前段に寄せた方が、リクエスト送信と切断の衝突を減らしやすいから。
- 06のローカル実装でも、`IDLE_TIMEOUT_MS` を決める時は「誰が先に切るべきか」を意識すると理解が深まる。

## 6. 06実装で必要な設計

### 4-1. 最低限どこまで実装すればKeep-Aliveと言える？
疑問点:
- 「何を満たせば06として成立？」

こういう意味らしい:
- 同一ソケット内での読み取りループがあること。
- `Connection: close` を受けたら終了できること。
- アイドルタイムアウトと最大リクエスト数で接続を回収できること。

### 4-2. `Content-Length` 読み切りはなぜ必要？
疑問点:
- 「GET中心なら本文消費は後回しでもよい？」

こういう意味らしい:
- 読み残しがあると、次リクエストの先頭と混ざって境界が壊れる。
- keep-aliveでは同一ストリームを継続利用するため、特に重要。

## 7. よくある詰まり

### 5-1. keep-aliveにしたはずなのに再利用されない
疑問点:
- 「なぜ毎回新規接続になる？」

こういう意味らしい:
- 1レスポンスごとにソケットを閉じている可能性が高い。
- レスポンスに `Connection: close` を常に返している可能性もある。
- まずは接続ループの継続条件を確認する。

### 5-2. 動いているのに突然切れる
疑問点:
- 「途中で接続が切れるのは不具合？」

こういう意味らしい:
- 設定した timeout や最大件数で意図的に切れているケースがある。
- 異常切断か設計どおりかを、サーバーログと `curl -v` の両方で判断する。

## 8. 最短チェック（これだけは確認）
1. `curl -v http://localhost:8080/ http://localhost:8080/hello` で再利用ログが出る。  
2. `curl -v -H 'Connection: close' ...` で切断ログが出る。  
3. timeout または max requests 到達時に、どちらが切断主導かを説明できる。  
4. 「サーバー先行切断だと競合が起き得る」ことを、自分の言葉で説明できる。
