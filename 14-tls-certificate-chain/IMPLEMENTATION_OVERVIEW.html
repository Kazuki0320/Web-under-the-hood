TLS証明書チェーンの仕組み — TlsCertificateInspector 実装前の整理

作成日: 2026-11-01 ／ 対象: Web-under-the-hood 14-tls-certificate-chain ／ 言語: Java（標準ライブラリのみ）

概要

Java標準の SSLSocket で example.com:443 にTLS接続し、サーバーから届いた証明書チェーンと、Javaが信頼しているルートCA（トラストアンカー）を表示する小さなCLIツールを作る。ブラウザが裏で行っている「この証明書は信頼できるか？」の判断を、実物の証明書で観察するのが目的。

内部で起きていること（3Dモデル）

左が自分が作るJavaクライアント（TlsCertificateInspector）、右が接続先のサーバー（example.com。自分では作らない）。ステップを進めると、証明書がどこからどこへ移動し、どこで検証されるかが分かる。

3Dの描画には three.js（CDN）への接続とWebGLが必要です。下のステップ説明は読めます。

今回の問い

  • サーバー証明書は、誰の署名によって「本物」と判断されるのか
  • ルートCA証明書はサーバーから届かないのに、Javaはどうやってチェーンを完成させるのか
  • Javaのどの処理（API）が、どの検証を担当しているのか

結論

信頼は「サーバー証明書 → 中間CA → ルートCA」と Issuer（署名者）をたどって 決まる。サーバーが送るのは通常サーバー証明書と中間CAまでで、最後のルートCAはJava自身のトラストストアにあるものと突き合わせる。

要点

  • 検証の実体は startHandshake() の内部（JSSE）。期限・署名・ホスト名・ルートへの到達を確認し、失敗すれば SSLHandshakeException。
  • SSLSocket を直接使う場合、ホスト名検証は setEndpointIdentificationAlgorithm("HTTPS") で明示的に有効化する。
  • 実装ステップ6（ルートCA探索）は、JSSEが内部で済ませたことを学習用にアプリ側で再現する処理。

仕組み

登場人物は4つ。自作アプリ（TlsCertificateInspector）、Java内部のTLS実装（JSSE / SSLSocket）、接続先サーバー、Javaのトラストストア（cacerts）。

確認できた事実

TLS 1.3（RFC 8446）では、トラストアンカーとなる証明書はチェーンから省略してよい（MAY）とされている。またTLS 1.3では Certificate メッセージ自体も暗号化されて届く。

確認できた事実

javax は「Java の拡張（eXtension）」の意味で、もともと標準とは別に追加する拡張ライブラリに付けられた名前。今回使う javax.net.ssl（TLS の実装＝JSSE）は、現在は JDK に最初から入っている標準機能で、追加のインストールは要らない。

Socket は「通信の口」で合っている？

合っている。もう少し正確に言うと、ソケットは OS が用意する通信の出入り口 で、「IPアドレス＋ポート番号」で場所が決まる。Java の Socket オブジェクトは、その OS のソケットを操作するためのハンドル。SSLSocket は、その口に「暗号化と証明書の確認（TLS）」を足したもの。

SSLSocketFactory は何をしている？

「TLS の設定が済んだソケット（SSLSocket）を作る工場」。工場の中に「どのルートCAを信頼するか」「どの TLS バージョン・暗号スイートを使うか」といった設定を持っていて、作るソケットすべてにその設定を引き継ぐ。

  • 中に持っている設定（SSLContext）： 信頼するルートCAの一覧（トラストストア cacerts）、使ってよい TLS バージョン、暗号スイート、必要なら自分の証明書（今回は使わない。mTLS で使う）
  • getDefault()： Java 標準の設定（JDK 付属の cacerts など）が入った工場を返す。戻り値の型が親の SocketFactory なので、(SSLSocketFactory) でキャストする
  • createSocket(host, port)： 工場の設定を引き継いだ SSLSocket を作り、TCP 接続まで行う。TLS ハンドシェイクはまだ
  • なぜ工場を挟むのか： 設定を 1 か所にまとめ、どのソケットにも同じ設定を配るため。信頼するルートCAを変えたいときは、ソケットではなく工場ごと差し替える（例: テストで自分で作った CA を信頼させる → 独自の SSLContext から getSocketFactory() で工場を作る）
補足（要確認）

getDefault() は、特別な設定をしていなければ SSLContext.getDefault() の工場を返す（Java SE の API ドキュメントの記述による。細部は実装時に Javadoc で確認する）。今回のコードでトラストストアを一度も指定していないのに証明書の検証ができるのは、この標準設定に cacerts が入っているから。

    エンコードとデコード

    エンコード ＝ 情報を、決まった形式のバイト列（0〜255の数の並び）に変換すること。デコード ＝ その逆で、バイト列を読み取って元の情報（Java のオブジェクト）に戻すこと。証明書は通信では DER という形式のバイト列で運ばれ、Java が受け取るときにデコードして X509Certificate オブジェクトにしている。getEncoded() は、そのオブジェクトの元になったバイト列（エンコードされた形）を返す。

    • デコードとハッシュの違い： デコードは元に戻せる「変換」。SHA-256 は元に戻せない「要約」。同じ証明書からは必ず同じ 32 バイトになり、1 ビットでも違えば全く違う値になるので、証明書の見分けに使える（指紋）。
    • なぜ getEncoded() を使う： ブラウザなども「DER のバイト列」をハッシュして指紋を出しているため、同じ値になる。表示用の文字列（toString()）をハッシュすると、ブラウザの指紋と一致しない。
    • byte が負の数になる理由： Java の byte は -128〜127。String.format("%02X", b) は 0xB4 のような 0〜255 の見た目で表示してくれる（-76 → B4）。

    TrustManagerFactory の 3 ステップ（getInstance → init → getTrustManagers）

    TrustManagerFactory factory =
        TrustManagerFactory.getInstance(TrustManagerFactory.getDefaultAlgorithm());   // 1

    1. getInstance(...)： 工場の種類を決めて受け取る。この時点では、中身（信頼する証明書）はまだ空。
    2. init((KeyStore) null)： 工場に「信頼する証明書の一覧」を設定する。null は「Java 標準のトラストストア（cacerts）を使う」という意味。

    • init しないと： init の前に getTrustManagers() を呼ぶと、「まだ初期化されていない」というエラー（IllegalStateException）になる（Javadoc の記述による）。
    • SSLSocketFactory との違い： SSLSocketFactory.getDefault() は最初から設定済みの工場が返る。TrustManagerFactory は「受け取る」と「設定する」の 2 段階が必要。
    • null ではなく自分の KeyStore を渡すと： 自分で作った CA だけが入った KeyStore をファイルから読み込んで渡すと、その CA だけを信頼する判断係が作られる（テスト用サーバーを信頼させたいときに使う）。今回は標準の cacerts を使うので null。
    • (KeyStore) のキャストが付いている理由： init には受け取る型が違う 2 種類（init(KeyStore) と init(ManagerFactoryParameters)）がある。ただの null だと、どちらを呼ぶのか Java が決められずエラーになるため、(KeyStore) null と書いて「KeyStore の方」と指定している。

    • [3] は「中間CA」と表示されているが、実際はクロス証明書： ルートCA「SSL.com TLS ECC Root CA 2022」を、古いルート「AAA Certificate Services」が署名したもの。新しいルートを知らない古い端末でもつながるように、サーバーが付けて送ることが多い（今回の意図は推測）。CertificatePrinter は 0 番以外をすべて「中間CA証明書」と表示する作りなので、こう見える。
    • [3] は公開鍵が EC なのに、署名アルゴリズムが SHA256withRSA： 公開鍵は「持ち主の鍵」、署名アルゴリズムは「発行者の鍵」の話。発行者の AAA Certificate Services が RSA の鍵なので、RSA の署名になる。
    • [0] の Subject は CN=example.com だけ： ホスト名の確認は、実際には SAN（Subject Alternative Name）という拡張項目で行われる（今回のツールでは表示していない）。

    「ルートCAが見つからない」理由

    確認できた事実

    こちらの確認環境（OpenJDK 21）の cacerts には「SSL.com TLS ECC Root CA 2022」はあり、「AAA Certificate Services」はない（keytool で確認）。手元の JDK でも同じ可能性が高いが、未確認。

    • TrustAnchorFinder は、一番上の [3] の Issuer（AAA Certificate Services）を cacerts から探している → cacerts に無いので「見つからない」
    • 実際のルートは [3] の上ではなく、[2] の上（cacerts の SSL.com TLS ECC Root CA 2022）にあった
    • JSSE はハンドシェイクのときに、この別の経路（[0] → [1] → [2] → cacerts のルート）を組み立てて検証に成功している（ハンドシェイクが例外なく通ったことからの推測）
    改善（実施済み）

    一番上だけでなく、[0] から順に「この証明書の Issuer が cacerts にあるか」を調べ、最初に見つかったものをトラストアンカーとして表示するように main の Step 6 を変更した。
