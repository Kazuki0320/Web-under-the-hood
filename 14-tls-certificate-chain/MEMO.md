## 2026-11-01 実行結果からわかったこと（下書き：自分の言葉に直して使う）

実行: `java TlsCertificateInspector`（example.com:443）

1. チェーンは4枚だった
- [0] example.com → [1] Cloudflare TLS Issuing ECC CA 3 → [2] SSL.com TLS Transit ECC CA R2 → [3] SSL.com TLS ECC Root CA 2022（AAA Certificate Services が署名したクロス証明書）
- [0]〜[3] は、どれも「[i] の Issuer ＝ [i+1] の Subject」でつながっていた。

2. ルートCAは [2] の上で見つかった
- 最初は一番上の [3] の Issuer（AAA Certificate Services）だけを探していて「見つからない」になった。
- [0] から順に探すように直したら、[2] の Issuer「SSL.com TLS ECC Root CA 2022」が cacerts にあり、verify() でも署名を確認できた。
- [3] は、古いルート（AAA）しか知らない端末向けの「つなぎ」で、今回の Java の検証には不要だった。

3. ルートCAがサーバーから送られない理由（今回の結果で説明）
- クライアントは、自分のトラストストアにあるルートCAしか信用しない。サーバーからルートを送っても、手元の一覧と照らし合わせるだけなので意味が薄い。
- 今回サーバーが送ったのは、ルートと同じ名前の「AAA が署名した版」（[3]）で、ルートが自分で署名した本物ではなかった。Java は手元の cacerts にある本物を使った。

4. 表示の読み方で気づいたこと
- 公開鍵は「持ち主の鍵」、署名アルゴリズムは「発行者の鍵」。[3] は公開鍵が EC なのに、発行者 AAA が RSA なので署名は SHA256withRSA だった。
- サーバー証明書 [0] の有効期間は約3か月と短く、中間CAは10年以上と長い。

## 理解の確認（下書きの答え）

- ルートCAがサーバーから送られない理由: クライアントは自分のトラストストアのルートだけを信用するので、送っても照合に使われない。今回もサーバーはクロス証明書を送っただけで、Java は cacerts のルートで検証した。
- `[0]` の Issuer と `[1]` の Subject の関係: 同じ名前になる。[1] が [0] を発行（署名）した、という意味。
- JSSE が検証している4項目: 有効期限、署名、ホスト名、トラストストアのルートCAまでつながるか。
